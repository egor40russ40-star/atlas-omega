# ATLAS Mobile 2 — Этап 1. Требования и инварианты

Статус: **ЗАФИКСИРОВАНО**  
Назначение: определить границы новой архитектуры до написания новой версии APK.

## 1. Главная цель

ATLAS Mobile 2 — мобильная рабочая станция для управления ATLAS и полноценной работы с кодом с телефона. Центральный сценарий — быстрый, устойчивый и удобный терминал уровня специализированного SSH-клиента, а не вспомогательное окно внутри панели управления.

Приоритеты в порядке важности:

1. Терминал и написание кода с телефона.
2. Надёжность сессии при сворачивании, блокировке экрана и смене сети.
3. Полностью русскоязычный интерфейс приложения.
4. Безопасная идентификация устройства и хостов.
5. Совместимость с существующим ATLAS backend RC2 без разрушения уже работающего контура.
6. Минимум ручной настройки после первичного подключения.

## 2. Неподвижные системные инварианты

- `LIVE_TRADING_ENABLED = NO`.
- `live_trading_authority = ABSENT` для мобильного клиента.
- `RESEARCH_ONLY = YES`.
- Новое мобильное устройство никогда не получает доверие автоматически.
- Новое устройство не получает торговых полномочий.
- Работающий backend RC2 и NucBox-agent не изменяются без отдельного этапа совместимости и rollback.
- Старый APK не удаляется автоматически до прохождения real-device acceptance новой версии.
- Приватные ключи, пароли и токены не вшиваются в APK, Git и CI artifacts.
- Терминальный stdout/stderr, shell-команды, имена файлов и traceback не переводятся и не модифицируются приложением.

## 3. Обязательные функциональные требования

### 3.1 Терминал

Обязательны:

- полноэкранный терминал как основной экран;
- настоящий PTY;
- `xterm-256color` и ANSI/UTF-8;
- корректная работа `bash`, `zsh`, `vim`, `nano`, `micro`, `tmux`, `git`, Python и системных CLI;
- несколько терминальных вкладок;
- устойчивые серверные сессии через `tmux`;
- автоматическое переподключение после краткого обрыва сети;
- корректный PTY resize при повороте экрана, появлении клавиатуры и split-screen;
- scrollback, поиск, выделение, копирование и вставка;
- жест изменения размера шрифта;
- поддержка аппаратной клавиатуры;
- отсутствие Android autocorrect/predictive transformations внутри терминала;
- быстрый переход между терминалом, кодом, файлами и ATLAS.

### 3.2 Спецклавиатура программиста

Обязательны:

- `ESC`, `TAB`, `CTRL`, `ALT`, `SHIFT`;
- стрелки, `HOME`, `END`, `PGUP`, `PGDN`;
- быстрые `CTRL+C/D/Z/L/R/A/E/W`;
- программные символы `|`, `\\`, `~`, `_`, `-`, `{}`, `[]`, `()`, `:`, `;`, `=`, `+`, кавычки;
- режим latch/lock для `CTRL`, `ALT`, `SHIFT`;
- удержание стрелок и повтор;
- настраиваемые пользователем панели;
- минимум две пользовательские раскладки быстрых клавиш;
- кнопка скрытия/показа системной клавиатуры.

### 3.3 Русификация

- Русский — основной язык интерфейса.
- Все экраны, меню, статусы, ошибки, onboarding, настройки, подтверждения и справка имеют русские строки.
- Строки UI не хардкодятся в Compose; используются resources.
- Технические детали ошибки доступны отдельным раскрываемым блоком в оригинальном виде.
- В дальнейшем допускается английский как дополнительная локаль, но русский интерфейс не зависит от английской локали.

### 3.4 Код и файлы

Архитектура обязана предусматривать:

- дерево файлов удалённого проекта;
- открытие/редактирование текстовых файлов;
- поиск по файлам;
- быстрые действия Git status/diff;
- запуск выделенного кода/команды в выбранной терминальной сессии;
- переход по `path:line` из terminal output к файлу;
- сохранение недописанного локального буфера при сворачивании приложения.

Полноценный визуальный редактор может вводиться после стабилизации терминального ядра, но интерфейсные и доменные границы должны быть предусмотрены заранее.

## 4. Нефункциональные требования

### Надёжность

- Потеря Android-процесса не должна убивать удалённую рабочую сессию: `tmux` остаётся источником продолжения работы.
- После восстановления сети приложение должно уметь восстановить SSH и повторно присоединиться к ранее созданной `tmux`-сессии.
- Ошибка одной вкладки не должна разрушать остальные активные сессии.

### Безопасность

- Gateway: только HTTPS.
- SSH: строгая проверка host key после первичного подтверждения/managed enrollment.
- Host-key mismatch всегда блокирует соединение.
- Секреты не пишутся в обычный DataStore/SharedPreferences и не попадают в логи.
- Импорт существующего SSH-ключа допускается только как расширенный/аварийный режим.

### Производительность

Целевые критерии для acceptance:

- отсутствие заметной задержки интерфейса при обычном вводе команд;
- стабильный вывод длинных логов и команд с большим stdout;
- отсутствие OOM при четырёх открытых терминальных вкладках в типовом режиме;
- плавный scrollback и изменение размера терминала;
- reconnect без блокировки UI.

## 5. Поддерживаемая платформа

Текущая архитектурная база:

- Android minSdk 26;
- target/compile SDK 36;
- Kotlin + Jetpack Compose;
- Java 17 toolchain;
- terminal emulator: libvterm/ConnectBot termlib или совместимый адаптер;
- SSH transport: ConnectBot sshlib или заменяемая реализация за интерфейсом транспорта.

Версии библиотек не являются частью доменной архитектуры и могут меняться без изменения контрактов верхних слоёв.

## 6. Что не входит в первую новую реализацию

До отдельного решения не входят:

- торговые операции;
- live-trading authority;
- встроенный VPN/Tailscale userspace stack;
- root-доступ на телефоне;
- автоматическое sudo без подтверждения;
- облачное хранение приватных SSH-ключей;
- удаление старого мобильного клиента;
- изменение production RC2 API без compatibility gate.

## 7. Правило перехода к реализации

Писать новую версию APK разрешается только после фиксации всех архитектурных этапов и отдельной команды пользователя на реализацию.
